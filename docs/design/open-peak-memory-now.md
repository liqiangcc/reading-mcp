# Open peak memory, measured now (MEM-2a)

Measurement only: nothing the server does changes. The release server runs with
`READING_MCP_TOOLS=v1`, the default PDF backend, telemetry on for the RSS runs and off for the
heaptrack runs, on a fresh state directory per input. Every number below comes from one successful
run of `Memory profile (open peak, now)`:
[run 39822502855](https://github.com/liqiangcc/reading-mcp/actions/runs/39822502855), commit
`2f166a9`, built with `CARGO_PROFILE_RELEASE_DEBUG=line-tables-only`. The tables are generated by
`scripts/mem-profile-now.py report`; the workflow is `.github/workflows/mem-profile-now.yml`.

The task's bounds: **cjk-64mib** 2 x 64 MiB + 50 MB = **178 MiB**; **宋史** 2 x its largest section
(20,183 chars, about 60 KB) + 50 MB = **about 50 MB**.

## Method

- **RSS timeline.** One server process per input; `/proc/<pid>/status` (`VmRSS`, `VmHWM`) is sampled
  every 20 ms from process start through the first `open_document` return, through a 3 s settle
  (prewarm and other background work), then through one `get_document_structure`, one
  `get_text_units`, one `search_document`, a second 3 s settle, and a **second `open_document` of
  the same source in the same process**, then a final 3 s settle. `READING_MCP_TELEMETRY=1` makes
  the server write one JSON event per phase to stderr; each line is timestamped as it arrives, and
  its `duration_ms` turns it into a `[end-duration, end]` interval, so the samples align with
  `retrieve`, `parse`, `repository_save`, `text_unit_sets_write`, `index` and `scan_prewarm`. A
  phase's *max* is the largest sample inside its interval; the global peak is marked in the phase
  whose interval contains it (the most specific one when intervals nest, e.g. `scan_prewarm`
  inside the settle).
- **Itemised heap peak.** The same open under `heaptrack`, printed with
  `heaptrack_print --print-peaks=1 --peak-limit=200 --sub-peak-limit=40`; each allocation live at
  the global heap peak is bucketed by the nearest frame of this checkout (`src/...`, recovered from
  the file and line because inline collapsing leaves symbols like `poll<>::{closure#0}`), with the
  surrounding stack deciding SQLite bind/record/page-cache and `serde_json` output buffers.
  `MALLOC_ARENA_MAX=2` repeats every run.
- **Retained.** `VmRSS` 3 s after `open_document` returns versus the peak; the server exposes no
  `malloc_trim`, so the difference is what the allocator returned to the OS, not what a trim would.
- **SQLite facts.** Read directly from the fresh database after each run: the PRAGMAs, the stored
  `document_json` bytes, the `section_text_v2` bytes and every `document_meta_v2` blob.

## 4. Heap peak versus RSS peak

`heaptrack`'s heap peak is the bytes allocated and live; the RSS peak is the pages resident. The
difference is allocator fragmentation (free arenas not returned), thread stacks, SQLite's page
cache and mmap, and the tokio runtime.

| Input | Heap peak MiB | RSS peak MiB | Gap MiB | RSS peak under heaptrack, default MiB | RSS peak under heaptrack, arena2 MiB | Arena2 saves MiB |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| cjk-64mib | 233.3 | 256.4 | 23.1 | 263.8 | 261.1 | 2.7 |
| zh-large | 92.0 | 135.0 | 43.0 | 144.7 | 114.2 | 30.5 |
| en-novel | 18.3 | 43.2 | 24.9 | 47.0 | 41.3 | 5.7 |
| text-long-cjk-300 | 62.6 | 77.0 | 14.4 | 84.0 | 83.7 | 0.3 |
| text-long-en-300 | 6.1 | 24.3 | 18.2 | 29.6 | 27.4 | 2.2 |

For 宋史 the gap is 43 MiB and more than two thirds of it is allocator fragmentation: arena2 alone
removes 30.5 MiB of RSS without touching the heap peak. The rest is the SQLite page cache (0.2 MiB
here), the tokio runtime and thread stacks.

"Returned" is peak minus the RSS 3 s after `open_document` returned; "still resident" is that RSS
itself. The peak is transient: cjk-64mib returns 189.1 of its 256.4 MiB (74%) and 宋史 returns 36.0
of 135.0 MiB (27%). The second open of the same book in the same process re-reads the source (the
`retrieve` phase, which is why cjk-64mib's RSS rises to 158.8 MiB again) but hits the stored open
result, so it does not re-parse or re-index; after the resource is dropped it leaves 28 MiB more
resident than the first open for cjk-64mib and 12 MiB more for 宋史 (the prewarm and the second
response).

### (d) Window the segmentation and descriptor build of a very large single section

- **Removes.** 135.0 MiB of `text_unit_sets` for cjk-64mib: `build_segmentation_section_layout`
  77.8 MiB (59.4 + 12.7 + 5.7), `build_section_descriptors` 34.3 MiB (25.5 + 6.0 + 2.8),
  `walk_section_stream` 23.0 MiB (12.4 + 6.3 + 4.3). Windowed segmentation can also drop part of
  the 30.4 MiB `DocumentSegmentation`.
- **Code.** `src/infrastructure/sqlite.rs`: `build_segmentation_section_layout`,
  `build_section_descriptors`, `write_document_sections`, `SectionLayoutSource`;
  `src/application/text_unit_stream.rs`: `walk_section_stream`; `src/domain/segmentation.rs`:
  `collect_section_segmentation`. The chunk table already cuts the section into 3,195 chunks; the
  work is to emit each chunk's descriptors as it is cut instead of materializing the whole
  section's `Vec<LayoutSentence>`/`Vec<SentenceDesc>`/`HashMap`s first.
- **Byte-identical.** `section_layout_v2`, `section_layout_chunk_v2` (including the
  `coverage_*_json` totals), `section_text_v2`, `text_units`, the stored streams and every tool
  response.
- **Risk.** Medium-high: chunk boundaries, `first_*_index` fields and the coverage totals must
  match the current whole-section pass exactly.
- **Size.** Large.
- **Effect.** cjk-64mib: heap 233 -> about 98 MiB, RSS 256 -> about 130-150 MiB, inside the
  178 MiB bound. 宋史: near zero, because its largest section is 20,183 characters.

### (a) Build `normalized_block_map` straight into the compressor

- **Removes.** 32.0 MiB of the 宋史 heap peak (the JSON String's 32 MiB capacity for a 19.1 MB
  payload) and the 3.7 MiB `split_metadata` clone on en-novel. It does not remove the map
  structure the segmentation reads (7.0 + 5.6 + 3.1 MiB in the table).
- **Code.** `src/domain/normalized_block.rs`: `set_normalized_block_map`, `normalized_block_map`;
  `src/infrastructure/sqlite.rs`: `split_metadata`, `encode_metadata_value`, `save_shared`. Feed
  the map to `serde_json::to_writer` over the `ZlibEncoder` instead of `to_string` + clone.
- **Byte-identical.** `documents.document_json`, every tool response, and the stored
  `document_meta_v2.normalized_block_map` zlib blob if the level and the 1 MiB feeding chunks stay
  the same (a different feed size changes deflate block boundaries even at level 6).
- **Risk.** Medium: `Document.metadata` is a `String` contract the EPUB validator, the reliability
  inspector and `try_segmentation` read.
- **Size.** Medium.
- **Effect.** 宋史: heap 92 -> about 60 MiB, RSS about 135 -> 100 MiB (about 80 with arena2). Not
  50 MB alone.

### (c) Free the parsed EPUB trees section by section

- **Removes.** Part of the 29.4 MiB `parser_document` on 宋史: `render_blocks` 9.8 MiB,
  `build_section` 6.8 MiB, validation clones 5.7 + 2.6 MiB, `from_navigation` 1.0 MiB. The parser
  keeps `parsed_spine_documents` (all 543 parsed section trees) and `normalized_blocks` alive until
  `reconcile_epub_structure` has built `reconciled.root_sections`, so the section text exists at
  least twice at the peak.
- **Code.** `src/parsing/epub.rs`: `parse_sync_inner` (the `parsed_spine_documents` /
  `normalized_blocks` loop, and `reconcile_epub_structure`); `src/parsing/epub_structure.rs`:
  `reconcile_epub_structure`.
- **Byte-identical.** Section ids, order, titles, content, `epub_structure_map`, the validation
  report and the open result.
- **Risk.** High: reconciliation is identity-bound (`section://epub-N/...`), and the validation
  report is built from the reconciled document.
- **Size.** Large.
- **Effect.** 宋史: heap 92 -> about 72 MiB alone; with (a) about 40 MiB heap, RSS about 80.

### (g) True per-section streaming of the EPUB

- **Removes.** Holding all parsed trees, the whole `normalized_block_map` and the whole `Document`
  before saving. With (a) and (c) it removes about 61 MiB of the 92 MiB heap peak; the floor is the
  final 13.5 MiB of section text, 6.6 MiB segmentation, the 6.8 MiB input (moved into the text) and
  a per-section working set.
- **Code.** `src/parsing/epub.rs` (parse and reconcile per spine item), `src/application/open_document.rs`
  (`ingest`), `src/infrastructure/sqlite.rs` (`save_shared`, `write_document_sections`),
  `src/domain/segmentation.rs`. The open result, validation report and reading profile still need
  the whole document, so the end of the pipeline cannot be fully streamed without a second pass.
- **Byte-identical.** Every stored row, the open result and every tool response.
- **Risk.** Very high: the open becomes incremental across parser, repository, text-unit index and
  search index, and the validation/report stages consume the whole document.
- **Size.** Large.
- **Effect.** The only path to 50 MB for 宋史, and only combined with (a), (c) and (f); even then
  the estimate is about 45-60 MiB RSS, so it is tight.

### (f) `MALLOC_ARENA_MAX=2`

- **Code.** None in the server: an environment setting in the deployment unit and the CI probe.
- **Byte-identical.** Everything; the allocator only.
- **Risk.** Low; a throughput effect is possible and is not measured here.
- **Size.** Small.
- **Effect.** Alone not enough for 50 MB; it is part of the 宋史 combination.

### (b) Drop the raw-bytes copy as soon as parsing finishes

- **Code.** `src/parsing/pdf_v8.rs`, `src/parsing/pdf.rs`, `src/application/ports.rs`; keep the

- **Byte-identical.** Extracted text, page structure and the open result.
- **Risk.** Low-medium.
- **Size.** Medium.

## What did not run, and why

- **A larger EPUB.** The stress inputs contain no EPUB larger than 宋史 (6.84 MiB, 543 sections), so
  the sectioned-book case is 宋史 only.
- **`--malloc-arena-max` workflow input.** The workflow exposes it, but this run used the fixed
  `default` and `arena2` pair; no other arena count was measured.
- **The stress 1,000/1,500-page PDFs.** This task asks for 300-page CJK and English text PDFs, so
  the inputs are the generated `text-long-cjk-300` (13.7 MiB) and `text-long-en-300` (0.2 MiB); they
  are smaller than the stress PDFs, which is why the CJK PDF peaks at 77.0 MiB rather than the
  stress profile's ~135 MiB.
- **OCR / non-default PDF backend.** `READING_MCP_TOOLS=v1`, default backend, no OCR.
- **`malloc_trim`.** The server exposes none, so retained memory is reported as `VmRSS` versus
  `VmHWM` and the difference is what glibc returned, not what a trim would return.
- **A second open that re-ingests.** On main the second open is an open-result hit; a
  `force_refresh` second open was not measured.
