# Where a PDF open spends its time, and what lopdf 0.44 does with the `/ToUnicode` CMaps that lose text (PDF-2a)

Measurement and diagnosis only. **No product code changed**: the new files are
`scripts/pdf-open-profile.py`, `scripts/pdf-cmap-probe.py` and
`.github/workflows/pdf-open-profile.yml`. Every number below comes from run
[39773370640](https://github.com/liqiangcc/reading-mcp/actions/runs/39773370640)
(`pdf-open-profile.yml`, commit `b8a28e0` of `bench/pdf2a-open-time-cmap`), unless a sentence says
otherwise. A second run of the same tree ([39771933466](https://github.com/liqiangcc/reading-mcp/actions/runs/39771933466))
on a slower runner produced the same tables with the CJK opens 1.5x larger (49.6 s and 101.8 s
for 300 and 600 pages), so the shape is reproducible and the absolute seconds are runner speed.

## 1. What was measured

- **Inputs.** `text-long-{en,cjk}-{100,300,600}` generated by `scripts/pdf-gen-inputs.py` (called
  from the workflow, not edited): single-column A4, 9 pt, one font per page, NotoSansCJKsc
  embedded for the CJK variants, Helvetica for the EN ones. `paper-2col-cjk` (12 pages, same
  generator) for the CMap part. Real papers `2610.18269` and `2604.00909` (the two the PDF-1c
  note still reports as lossy) and three controls from the PDF-1b corpus:
  `2502.19428`, `2501.08197`, `2410.10278`. The two lossy papers are checked against the pinned
  `sha256` in `scripts/pdf-cjk-ids.txt`; the control papers are downloaded from arXiv.
- **Server.** `READING_MCP_TOOLS=v1`, OCR off, default PDF backend
  (no `READING_MCP_PDF_LAYOUT_PYTHON`), `READING_MCP_TELEMETRY=1`, one `open_document` per input
  in a fresh state directory.
- **CPU profile.** The release binary built exactly as `cpu-profile.yml` does:
  `CARGO_PROFILE_RELEASE_DEBUG=line-tables-only`, `RUSTFLAGS=-C force-frame-pointers=yes`,
  `perf record -F 999 -g --call-graph fp`, folded with the existing `scripts/perf-collapse.py`.
- **CMap probe.** PyMuPDF 1.28.2 `doc.xref_stream` for the decompressed `/ToUnicode`, PyMuPDF
  `page.get_text("rawdict")` for the reference text, and `scripts/pdf-cjk.py`'s font inventory
  and per-font survival method for the loss numbers.

### 2.4 Why: the CMap is re-parsed for every string shown, in a second pass

`text-long-cjk` has one font per page and one `/ToUnicode` stream of **256,880 bytes**. lopdf
resolves a font's encoding through `Dictionary::get_font_encoding_with_limit`
(`lopdf-0.44.0/src/object.rs:420-465`), which decompresses the `/ToUnicode` stream
(`object.rs:589-596`) and parses it (`encodings/cmap.rs:52-55`) with **no cache anywhere**.
There are two callers:

- `extract_page_texts_raw` (`src/parsing/pdf.rs:211-244`) calls
  `extract_text_chunks_with_limit` and `extract_text_with_limit` per page, and each resolves the
  encoding of **every font in the page's `/Resources`**
  (`lopdf-0.44.0/src/parser_aux.rs:115-130`). That is 2 parses per font per page, 600 for this
  document.
- `pdf_v8::PdfParser::parse_sync` (`src/parsing/pdf_v8.rs:29-51`) runs the above, and when the
  structure provenance is `inferred_numbered_headings` it reopens the PDF and calls
  `pdf_layout::extract_text_fragment_evidence`. That walker's `decode_text_object`
  (`src/parsing/pdf_layout.rs:418-438`) calls `get_font_encoding_with_limit` **for every string
  shown**. `text-long-cjk` shows 128 strings per page, so the second pass alone parses the same
  256,880-byte CMap 38,400 times.

The 100-page input never enters the second pass (100 sections for 100 pages = the page fallback,
which `pdf_v8` returns before the layout pass). The 300- and 600-page inputs do (9 sections for
300/600 pages = inferred numbered headings; the generated PDFs have no `/Outlines`), which is
the 22x per-page cliff. The papers do not: `2610.18269` has a 16-entry TOC and `2604.00909` a
20-entry one, so both take the `native_toc` path and never re-run the layout pass.

## 3. The `/ToUnicode` probe

Every CMap below is the decompressed stream; the first 1,500 and last 500 bytes of each are in
the `pdf2a-cmap` artifact (`<label>-<xref>.cmap.txt`). "lopdf resolves" is the share of the
source codes the document actually uses with that font for which the model of lopdf's parser
(`parser/cmap_parser.rs` + `encodings/cmap.rs` + `encodings/mod.rs:84-117`) returns something
other than U+FFFD. It is a model, not lopdf itself.

### 3.1 The construct that breaks the MuPDF-written CMaps: an odd number of hex digits in a destination

`paper-2col-cjk` and `text-long-cjk-100` carry a byte-identical 256,880-byte CMap (sha256
`cdfd56334bfc1742…`; the 300- and 600-page variants carry the same 256,880-byte stream). It has
111 `beginbfchar` sections, 46 `beginbfrange` sections, 15,627 destinations of which 13,743 are
single-unit, no array-form `bfrange`, no `usecmap`, 2-byte codespace,
`\n` line endings, no PostScript comment header, and **1,884 destinations with five hex digits**:

```
<e74c> <e751> <ffe9>
<e752> <e75c> <1f100>
<e75d> <e7b8> <1f110>
<e7b9> <e7f5> <1f170>
```

(`offset 90,248` of the stream). Those are the code points U+1F100..U+2xxxx that NotoSansCJKsc
covers; MuPDF writes the scalar value directly instead of a UTF-16BE surrogate pair. lopdf's
destination parser reads **two hex digits per code unit**:

- `lopdf-0.44.0/src/parser/cmap_parser.rs:255-257` (`hex_u16`) is
  `pair(hex_char, hex_char)`, i.e. exactly two digits;
- `:269-278` (`target_string`) is `many_m_n(1, 256, terminated(hex_u16, multispace0))` between
  `<` and `>`, so `<1f100>` fails on the leftover `0`;
- `:290-297` (`bf_range_line`) therefore fails, `:280-288` (`bf_range_section`) stops its
  `many0` before the line and then cannot find `endbfrange` at that position, so the **section**
  fails;
- `:214-216` (`cmap_codespace_and_mappings`) is `many1(alt(...))`, which keeps the sections
  parsed so far and returns the input at the failing section (byte 89,608);
- `:90-111` (`cmap_data`) then fails to match `endcmap`, so `cmap_stream` (`:29-36`) fails and
  `ToUnicodeCMap::parse` (`encodings/cmap.rs:52-55`) returns an error;
- `object.rs:452-463` turns that error into `Encoding::OneByteEncoding(STANDARD_ENCODING)`, which
  decodes each **byte** of a 2-byte CID as a Latin-1 character: the garbage text.

The bad lines are in a section whose glyphs the document never uses, so **one unused,
non-conformant line rejects the whole CMap**: lopdf resolves 0 of the 3,684 codes
(353,186 instances) of `text-long-cjk-100` and 0 of 309 codes (26,291 instances) of
`paper-2col-cjk`, while a permissive reader resolves 100% of them. That is the 0.000-similarity
garbage the PDF-1c note reported for the generated CJK inputs.

`scripts/pdf-cmap-probe.py --selftest-out` prints the verdicts in the artifact

`tag b'endcmap' at 238` — the parser is left at the failing section, exactly as described above.
Changing that one line to `<D83CDD00>` or dropping it makes the whole 256,880-byte CMap parse.

### 3.6 What "loss" means in these numbers

- The reference text is PyMuPDF's `get_text("rawdict")`, which for a code missing from
  `/ToUnicode` substitutes the CID as a code point (2604.00909: `䛾` for `<46FE>`). A "lost"
  character there is not text either implementation recovers.
- `per_font_survival` is character containment with a per-character claim budget, claimed in
  font-xref order. A font without a usable encoding still claims the characters another font
  returned (2610.18269: 47 of 76).
- The lopdf resolution rates come from a Python port of the parser and decoder, applied to the
  same bytes; they are not a counter inside lopdf.

## 4. What this implies (options and expected effect, no decision)

1. **Cache the parsed font encoding per font object across pages and across the two passes**
   (in our code: a pre-pass that resolves each `/ToUnicode` once and reuses it, or a
   `HashMap<ObjectId, Encoding>` threaded through extraction). Measured basis: 39,000 parses of
   the same CMap at 0.82 ms each are 32.1 s of the 32.24 s CJK open, and the same document at
   100 pages (200 parses) opens in 0.48 s. Expected effect: the 300-page CJK open drops to
   about three times the measured 100-page open (order 1-2 s instead of 32 s), because the
   per-page content walk and the structure work remain; the EN open is unaffected (it has no
   `/ToUnicode`). The second pass alone is 95.2% inclusive of the open and
   contributes front-matter evidence for one page, so caching inside it is where the win is.
2. **Normalise the CMap text in the PDF-1c in-memory pre-pass**
   (`src/parsing/pdf_text_repair.rs`, which already rewrites `/ToUnicode` streams) — rewrite an
   odd-length destination `<1f100>` to the UTF-16BE pair `<D83CDD00>` (or drop the line when the
   code is unused). Expected effect: the MuPDF CMaps parse, so `paper-2col-cjk` and
   `text-long-cjk` stop reading as garbage (0% -> ~100% of the used codes in the model); cost is
   one pass over the CMap per font (256 KB), not per page. Risk: it also changes what the
   fragment-evidence pass sees, and it is a second interpretation of a non-conformant CMap that a
   spec-strict reader would also reject.
3. **Do nothing.** CJK opens stay at 32-50 s per 300 pages (107-165 ms/page) and
   MuPDF-generated CJK PDFs stay unreadable in the default backend.
4. **Separately from the CMap work:** the 2604.00909 residual is a CMap coverage gap plus the
   reference text's CID-as-code-point fallback, and 2610.18269's is a font with no `/ToUnicode`
   at all plus the claim-order accounting. Neither is fixed by 1 or 2, and the PDF-1c note's
   attribution of both to "the same CMap-parse limitation" should be corrected.

## 5. What did not run

Nothing in the workflow failed: build, inputs, profile, cmap and aggregate all succeeded in run
39773370640 (9m8s) and in the two earlier runs of the same tree. Not measured, deliberately:

- the layout (PyMuPDF) backend: out of scope, and the PDF-1b note already shows it refuses every
  paper that loses CJK text;
- `paper-2col-cjk` and `text-long-cjk` *in the layout backend*; only the default backend is
  measured;
- the 1,000-page BENCH-S input: the scaling curve is already linear at 300 -> 600 pages, and a
  1,000-page CJK open would add ~110 s for one more point;
- a real lopdf call counter: lopdf is a dependency, not our code, so the per-page parse count is
  a model (2.4) corroborated by the profile, and the resolution rates are a Python port (3.1).
