# The open peak of a large PDF (PDF-2c)

One open of a large PDF held far more memory than the text it extracts: 284.1 MiB of peak RSS for
`2401.14345`, a 36-page paper whose extracted text is 89 KB. RSS does not come back down
afterwards, so a service pays that peak for every big PDF it opens. This note measures where the
peak comes from and what each reduction bought. It changes no output: every number below comes
from the same build shape and the same inputs, and the ingest parity gate proves the text,
sections, sentences, locators and cursors are unchanged.

Measurement only, no caching and no memo table: a read still costs O(page) through the indexed
rows, and an open still parses the PDF it was given.

## Method

`.github/workflows/pdf2c-measure.yml` (added by this work) builds the release binary with
`CARGO_PROFILE_RELEASE_DEBUG=line-tables-only` and, for each input on a fresh state directory:

* opens it once through the real server (`READING_MCP_TOOLS=v1`, OCR off, default PDF backend,
  `READING_MCP_TELEMETRY=1`) with `scripts/pdf-open-profile.py --mode run`, which reports the wall
  time, the peak RSS from `wait4`'s `ru_maxrss`, the RSS and high-water mark the server's own
  telemetry carried after each phase, and — new in this work — the server's `VmRSS` sampled from
  `/proc` the moment `open_document` returned (`scripts/memory-profile.py --retained-rss`): the
  memory the open leaves resident, which the peak alone cannot show;
* opens four of them again under `heaptrack` (`scripts/memory-profile.py --wrapper "heaptrack -o
  heap/{label}"`) and prints the peak heap with its top consumers, each named by the nearest frame
  of this checkout;
* reads the stored rows with `scripts/sqlite-facts.py` for the extracted text bytes, so the peak
  can be put next to the text it produced.

The inputs are the five heaviest documents of the PDF-5a sweep plus the 490-page `2305.18793`,
downloaded from arXiv and checked against the `sha256` in `scripts/pdf-sweep-ids.txt`, and the
synthetic text PDFs generated by `scripts/pdf-gen-inputs.py` (100 and 300 pages, English and CJK).
"Before" is `origin/main` at `6299698` (the tree with only the measurement commit added); "after"
is this branch's head.

## 2. The holders

`heaptrack_print --print-peaks` on `2401.14345`, with everything that is live at the global peak:

| holder | where | live at the peak |
| --- | --- | ---: |
| the first object tree, loaded to count pages | `src/parsing/limited_pdf.rs:21` (`Document::load_mem`), kept until the delegated parse returned | **93.14 MiB** (46.57 MiB of it stream payload from `_indirect_object::parse`) |
| a second copy of the whole file | `src/application/ports.rs:37` (`RetrievedResource::bytes`), cloned at `src/parsing/pdf_v8.rs:26` | **47.68 MiB** |
| the file itself | `src/retrieval/file.rs:95` (`tokio::fs::read`), held by the parse until it returned | **47.63 MiB** |
| the repair copy of the object tree | `src/parsing/pdf_text_repair.rs:42` (`pdf.clone()`) | **46.86 MiB** |

That is four full copies of the document's bytes and trees, live at the same instant, for a
document whose text is 89 KB. The same three sites lead on the text PDFs, where the text copies
join them: on `text-long-cjk-300` the peak consumers include `source_fragments` and the section
build (`src/parsing/pdf.rs:474`, `:572`, `:819` in the before tree), each a full copy of the page
text.

None of these is a bind copy: `document_json` for `2401.14345` is 9,498 bytes, and the save's
transient copy of it is not a holder at any of these peaks.

Peak heap (heaptrack) moves with it: `2401.14345` 278.6 → 231.0 → 123.5 MiB, `2403.19144` 232.8 →
118.5, `text-long-cjk-300` 122.7 → 58.6, `text-long-en-300` 60.8 → 30.8 MiB.

What each lever bought:

1. **Release the raw bytes and the repair copy as soon as the pages are read**
   (`load_and_release`, and the repair copy scoped to the page text). 45.8 MiB on
   `2401.14345` (−16%), 12.0 MiB on `text-long-cjk-300` (−9%). The repair copy only exists for
   documents that need it (CJK form XObjects or `uniXXXX` fonts) — `2401.14345` does.
2. **Load the object tree once per open.** `LimitedPdfParser` used to load the whole file to count
   its pages and keep that tree across the delegated parse, `pdf_v8` cloned the whole
   `RetrievedResource` to reload the PDF for the front-matter evidence, and the inner parser loaded
   it again. The tree is now loaded once, the page limit is checked on it, and it is handed to the
   builder and the evidence pass. **103.2 MiB on `2401.14345` (−43%, and −52% cumulatively)**,
   46.9 MiB on `text-long-cjk-300`, 23.1 MiB on `text-long-en-300`. This is the lever that matters.
3. **One content walk per page.** `extract_page_texts_raw` called the chunks variant and the text
   variant for the same page, so every page's streams were decompressed twice and every
   `/ToUnicode` CMap parsed twice. The peak does not move (the extra copy is per page), but the
   open time halves on the long documents: `text-long-cjk-300` 2.119 s → 1.413 s, `p2305.18793`
   1.362 s → 0.852 s, `p2510.07408` 1.126 s → 0.727 s.
4. **Stop copying the PDF's text at the section build.** The fragment list was built twice (once
   for the heading inference, once for the inferred section build) and the page-fallback path
   cloned each page's text into its section. Within the run-to-run noise of ±2 MiB on these inputs;
   it removes two full copies of the text and is what the CJK-300 peak's own consumers named.
5. **Release the object tree before the sections are built.** No measurable change on these ten
   inputs: the peak is at the load (file + tree) or while the page text and the fragment list
   exist, and the one structure that needs a second look at the tree (inferred numbered headings)
   keeps it anyway. Kept because it is a strict reduction in what the section build is built
   beside, and it makes the ownership explicit; it is the first thing to drop if this code has to
   shrink.
6. **Move the page chunks into the fragment list** instead of cloning them. Within the noise on the
   image-heavy documents, 2.7 MiB on `text-long-en-300` (−5% of that document's peak) and it
   removes the last full copy of the text.

## 5. What is left, and what was not done

* **The floor is now the load: the file plus its object tree.** For `2401.14345` that is 45.4 MiB
  of bytes plus a 90 MiB tree, live together while `lopdf` parses, and that is the 135.8 MiB peak.
  The absolute target of "2× the largest page's text + 50 MB" (about 50 MiB here) is not reachable
  from this shape: the text is 0.2% of the file, and the parse must read the whole file and build
  an owned object tree of every stream before it can read a page. Reaching it needs a streaming
  load (`Document::load` from a reader instead of `load_mem` from a slice), which the retriever
  cannot offer today — it hands the parser a `Vec<u8>`.
* **The image streams are never read.** After the load, the tree holds every image's compressed
  bytes and no code path decodes them (the raster coverage walk reads image *dictionaries* only).
  Releasing them right after the load would not lower this peak — the peak is during the load — but
  it would cut what stays resident afterwards. It is a separate, larger change (it must not touch
  the streams a form or a page content stream needs) and was not attempted here.
* **The bind copy at save time was not removed.** `SqliteDocumentRepository::save_shared` binds
  `document_json` with `params![]`, and rusqlite binds text with `SQLITE_TRANSIENT` — it copies
  the string into SQLite's own memory (`rusqlite-0.40.1/src/statement.rs:665`). The only way to
  bind without that copy is `raw_bind_parameter`, which binds a blob, and a blob is a different
  stored value (`typeof(document_json)` changes), so the stored bytes would change. Not done: the
  copy is also not a holder at any PDF peak measured here (`document_json` is 9,498 bytes for
  `2401.14345`, 234,433 bytes for the 490-page document).
* **Not measured here:** the layout/OCR backend (`pdf_layout_python`), which runs a Python worker
  in its own process and does not share this parse path; EPUB and text inputs, which this task did
  not touch; and any PDF larger than the 55.7 MiB corpus maximum.
