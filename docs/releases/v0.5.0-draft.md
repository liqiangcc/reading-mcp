## 1. What changes for a client

### 1.1 the default tool set is v2

The default `tools/list` is no longer the nine v1 tools. A process started without
`READING_MCP_TOOLS` now advertises **seven** tools:

| v2 tool | what it does | the v1 work it covers |
| --- | --- | --- |
| `browse` | directory navigation and document discovery in the authorized source workspace | `list_directory`, `list_documents` |
| `open` | opens a document and returns a short document handle | `open_document` |
| `outline` | the section tree as handles, titles, levels and sizes | `get_document_structure` |
| `read` | one reading item per call, in body order, with the next handle | `read_document`, `get_text_units` |
| `search` | lexical search; hits come back as handles and snippets | `search_document` |
| `cite` | the full `TextLocator` for a handle — the only v2 tool that returns a locator | the locator that only `search_document` / `get_text_units` could return in v1 |
| `source_view` | the identity-bound original visual source at a precise position (PDF page fidelity) | `get_source_view` |

Handles are short strings, not locators:

```text
d<doc_key>~<chk>                        document, e.g. d3~9f2c
d<doc_key>~<chk>.s<section_key>         section,  e.g. d3~9f2c.s12
d<doc_key>~<chk>.s12.p<paragraph>       paragraph (1-based)
d<doc_key>~<chk>.s12.p4.<sentence>      sentence  (1-based)
r:<section>.<S|P>.<position>            forward cursor
b:<section>.<S|P>.<position>            backward cursor
```

`doc_key` is `text_unit_documents_v2.doc_key`; `chk` is the first four lowercase hex digits of
SHA-256 over `document_id | normalized_document_hash | TEXT_SEGMENTATION_VERSION`
([`src/application/short_handle.rs`](../../src/application/short_handle.rs),
[`docs/runtime-configuration.md`](../runtime-configuration.md#tool-setreading_mcp_tools)).

**Nothing is removed.** Both older sets are still selectable, and the v1 surface is byte-identical
to v0.4.11:

```text
READING_MCP_TOOLS=v1     the nine v1 tools (their tools/list is byte-for-byte the v1 list)
READING_MCP_TOOLS=both   16 tools
unset / empty            v2 (seven tools)
```

The nine v1 names that remain behind `READING_MCP_TOOLS=v1` are `open_document`,
`get_document_structure`, `get_text_units`, `read_document`, `search_document`, `get_context`,
`get_source_view`, `list_documents` and `list_directory`. An unknown `READING_MCP_TOOLS` value is a
startup error, and an unregistered tool is not in `tools/list` and answers `tool not found`.

A host whose service configuration and acceptance still expect nine tools must set
`READING_MCP_TOOLS=v1` in that service's environment; this repository does not change a deployed
unit ([`docs/production-deployment.md`](../production-deployment.md)).

### 1.2 changed error texts and hints

**`ocr_required` replaces two wrong answers for an image-only PDF (PDF-4a, #224).** Before, a scan
either opened `ok` with almost no text (`/root/mcp-data/doc/naturebp.pdf`: 4 pages, 156 characters of
watermark) or failed as `unreadable` with the hint "the format or encoding is unsupported"
(a 99-page pure scan: 197 image objects, no fonts at all). Both now answer `ocr_required`, and the
error carries what was measured. The v1 message is unchanged, byte for byte
([`docs/design/pdf4a-image-only.md`](../design/pdf4a-image-only.md)):

```text
this PDF has no text layer (4 pages, 156 characters); it needs OCR
```

**The v2 hint now says what the PDF lacks and what the reader can do (PDF-4b, #231).** It used to be
one fixed sentence that only advised enabling OCR — something a reader of the deployed server cannot
do. The wire error object is unchanged (`error`, `hint`, optional `retry`); only the hint text
changed ([`docs/design/pdf4b-ocr-required-hint.md`](../design/pdf4b-ocr-required-hint.md)):

```text
该 PDF 没有可用的文字层（4 页只取到 156 个字符），需要 OCR：请改用带文字层的版本（例如离线 OCR 后的 PDF 或文本），或在支持 OCR 的服务上重新 open。
```

**Fewer PDF paragraphs come back as one coarse item (PDF-6d, #237).** The `#139` fallback guard no
longer counts a `digit→uppercase` junction when the uppercase run is exactly one capital that ends
its token, so `7B`, `3D`, `2K`, `Fig. 3A` stop making an undamaged paragraph ineligible for sentence
splitting. It is PDF-only: `TEXT_SEGMENTATION_VERSION` is not bumped and every stored EPUB handle
stays valid. The guard's other four junction kinds, its threshold of 3 and its doubled-token and
bibliographic rules are untouched
([`docs/design/pdf6d-guard-false-glue.md`](../design/pdf6d-guard-false-glue.md)).

**No new response field.** `V2-KIND` (`fix(v2): mark a whole paragraph returned in sentence mode`) is
**not** in this release: it is still an open PR (#234, §8). A v2 `read` item today still reports a
whole coarse paragraph only through the degradation reason carried by the v1 `get_text_units`
surface.

### 1.3 behaviour changes a client will notice without a contract change

- **Reopen no longer re-parses.** A second `open` of the same bytes under the same parser identity
  returns the stored open result (#173).
- **Search reads stored section text instead of an FTS5 index.** Results are unchanged by
  construction (`tests/lexical_scan_parity.rs`); first-search latency changed (§3, #187/#194/#229).
- **State is always SQLite.** The in-memory/temporary-directory mode is gone (#169).
- **The parsed cache is PDF-only** (#193): EPUB, HTML, Markdown and plain text are re-parsed on
  demand instead of being kept on disk, and the old `<state>/cache/parsed` directory is deleted once
  at startup.
- **A stale state directory is pruned at startup.** Open results written by another store version,
  and documents no open result references any more, are deleted in a bounded sweep (64 documents per
  start) with a `storage_prune` telemetry event (#230).

### 2.1 what happens on the first open after the upgrade

The open-result fingerprint is
`OPEN_RESULT_VERSION | NORMALIZATION_VERSION | NORMALIZED_DOCUMENT_HASH_VERSION |
TEXT_SEGMENTATION_VERSION | READING_PROFILE_SCHEMA_VERSION | index version | precise | reliability |
ingest fingerprint | TEXT_UNIT_STREAM_VERSION | TEXT_UNIT_STORE_VERSION`, and the ingest fingerprint
carries `PDF_TEXT_EXTRACTION_VERSION`
([`src/application/open_document.rs`](../../src/application/open_document.rs),
[`src/runtime/mod.rs`](../../src/runtime/mod.rs)). Because `TEXT_UNIT_STORE_VERSION`,
`PDF_TEXT_EXTRACTION_VERSION`, `LEXICAL_SEARCH_INDEX_VERSION` and `OPEN_RESULT_VERSION` all changed,
**every stored document re-ingests once on its next open**, and PDFs also miss the parsed cache.

Concretely, on the first open after the upgrade:

1. The stored open result no longer matches → the document is parsed again and the derived TextUnit
   index is rewritten into the current layout
   (`text_unit_documents_v2` … `section_layout_chunk_v2`, `section_text_v3`).
2. The old schema rows for that document are replaced in one transaction; a document stored by an
   older **section-row** shape is dropped and recreated by `SqliteDocumentRepository::open` in the
   same open that carries the `v11` bump, and a stale document is an explicit `StaleDocument` error,
   never an empty book ([`docs/design/sec3c-compact-locations.md`](../design/sec3c-compact-locations.md)).
3. At startup, the bounded prune removes open results of another store version and any `documents`
   row no open result references, with a `storage_prune` telemetry event
   ([`docs/design/storage1-prune-stale-rows.md`](../design/storage1-prune-stale-rows.md)).

### 2.2 old locators and handles

- **v1 `TextLocator` and v1 cursors stay valid.** Their identity inputs are `document_id`, the
  content hash, `NORMALIZATION_VERSION` and `TEXT_SEGMENTATION_VERSION`; none of those moved, so a
  locator or cursor saved at `v0.4.11` still resolves. `NORMALIZED_DOCUMENT_HASH_VERSION` and
  `TEXT_UNIT_ID_VERSION` also did not move.
- **v2 short handles can go stale, and they fail closed when they do.** A handle carries
  `doc_key` (a store-assigned row key) plus the four-hex-digit identity checksum. A re-ingest
  re-inserts the document row, so `doc_key` may change; a handle whose `doc_key` resolves to nothing
  answers `stale_handle`, and a handle whose `doc_key` now belongs to another document fails the
  checksum comparison instead of silently reading a different book
  ([`src/application/short_handle.rs`](../../src/application/short_handle.rs),
  [`src/application/read_reading.rs`](../../src/application/read_reading.rs)). A client that keeps
  handles across the upgrade should re-`open` and re-acquire them.
- **Nothing is lost that cannot be rebuilt.** Canonical documents, raw cache and parsed cache
  survive; only derived indexes and open results are rewritten.

## 4. known limits

- **PDF line reconstruction is still the biggest text-quality gap (PDF-6a).** Of 79 553 units over
  121 arXiv papers, 2 672 are longer than 800 characters and 2 468 of those (92.4 %) are whole
  paragraphs the `#139` guard refused to split; 860 long units are words glued across a chunk
  boundary in 16 papers, 74 short units are hyphen fragments and 45 header/footer lines reach the
  reader as their own text. Median 5-gram containment against an independent extractor is 0.982,
  with 14 of 121 papers below 0.9 ([`pdf6a-text-quality`](../design/pdf6a-text-quality.md)).
- **The PDF-6d narrowing is deliberately partial.** It removes one of five missing-space junction
  kinds and only in a one-capital shape; `474GB` still counts, and no density threshold is
  implemented — PDF-6d reports it as a question for the user rather than a change
  ([`pdf6d-guard-false-glue`](../design/pdf6d-guard-false-glue.md) §7).
- **A scanned PDF needs OCR; it is not readable without it.** With OCR off (the default) an
  image-only PDF now says so instead of pretending to be `ok` (§1.2). The v2 hint names the two
  routes that actually work: a copy with a text layer, or a server that runs OCR.
- **A large PDF's open peak has a hard floor.** It is the file plus its `lopdf` object tree for the
  duration of the parse: 45.4 MiB of bytes plus a 90 MiB tree for `2401.14345`, which is the
  135.8 MiB worst case ([`pdf2c-open-memory`](../design/pdf2c-open-memory.md) §6).
- **One 64 MiB single-section text still misses its memory bound** at 254.6 MiB RSS / 233.3 MiB heap
  peak against 178 MiB, and `en-novel`'s EPUB heap peak is 14.7 MiB against a 14 MiB target
  ([`open-peak-memory-now`](../design/open-peak-memory-now.md) §6, PR #220).
- **Very large single sections are not warmed for search.** A 64 MiB single section is skipped by the
  bounded warm (8 MiB per-section rule), so its first search stays at ~850 ms against a 100 ms target;
  `en-novel`'s first search measured 44.2 ms against a 40 ms gate on the slower runner that ran the
  comparison (PR #229 body).
- **No PDF layout-backend measurement exists yet.** Every PDF number above is the default backend
  with `READING_MCP_PDF_LAYOUT_PYTHON` unset; PDF-7a is an open PR (#238), not a merged result
  ([`pdf6a-text-quality`](../design/pdf6a-text-quality.md), "What did not run").
- **The PDF corpora are arXiv-only** (121 CC-BY/CC-BY-SA/CC0 papers, 4 842 pages). They contain no
  scans, no non-arXiv publishers and no CJK books; the CJK evidence is the 25-paper `pdf-cjk` corpus.

## 7. the version choice: 0.5.0

`Cargo.toml` says `0.4.11`; `v0.4.11` is the last tag. The protocol's pre-1.0 SemVer rule
([`docs/release-process.md`](../release-process.md) §2) reads, verbatim:

> - Patch：向后兼容的 bug、security、correctness、文档或运行时修复，例如 `0.1.0 -> 0.1.1`。
> - Minor：新增向后兼容能力，或 pre-1.0 阶段发生明确的用户可见破坏性 contract 变化，例如
>   `0.1.x -> 0.2.0`。

That is: a patch is a backward-compatible fix; a **minor** is a new backward-compatible capability,
**or an explicitly user-visible breaking contract change in the pre-1.0 phase**. The decision:

- The default tool contract changed visibly: `tools/list` is seven tools where it used to be nine,
  and a client that calls `open_document` without setting `READING_MCP_TOOLS=v1` now gets
  `tool not found`. That is a user-visible breaking contract change, so this is **not** a patch.
- Nothing here justifies a jump past 0.5.0: there is no 1.0.0 and no major-version rule applies
  (major is reserved for breaking changes after 1.0.0), and 0.5.0 is the next minor after 0.4.x.
- The stored-data migration (forced one-time re-ingest) does not raise the number further: §2 does
  not make persistence compat a separate version axis, and the protocol only requires that an
  undeclared data/identity incompatibility be a blocker — this one is declared here, in §2.

**Therefore: `0.5.0`** — minor, because the default tool set changed visibly. A release that only
carried the fixes (PDF-4a hint, PDF-6d, the storage and performance work) with the v1 default
unchanged would have been `0.4.12`.

## 9. suggested one-paragraph Release body

Written in the style of the v0.4.x release notes, short enough to paste into the GitHub Release; it
cites only numbers that §1–§4 source.

> Release v0.5.0: the default tool set becomes v2 (seven short-handle tools: `open`, `read`,
> `browse`, `outline`, `search`, `cite`, `source_view`); the nine v1 tools stay available behind
> `READING_MCP_TOOLS=v1`. Image-only PDFs now answer `ocr_required` with the measured page and
> character counts instead of opening empty or reporting `unreadable`. Stored data migrates once:

> stay valid, v2 handles may report `stale_handle` and never rebind silently. Measured since

> 121-paper sweep, PDF open time median 0.069 → 0.039 s, `宋史` lexical search 455.89 → 60.51 ms
> worst case and first search after open 226.5 → 33.9 ms, and 2 instead of 9 of 25 CJK papers losing
> more than 5 % of their characters. See `docs/releases/v0.5.0-draft.md` for every number and its
> source.
